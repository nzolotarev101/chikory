# bench-p3-rung-4-2026-08-03 (hand-run Chikory arm) — a survivable quota wall cost 18 hours, three unsealed runs, and a headline number that disagreed with itself

**Plain:** We ran the five-task benchmark by hand and it reported a 93% score. That score is not
usable. A real Gemini credit outage did happen — but the run was supposed to survive it, and eight
separate defects turned a wall that clears itself in a few hours into eighteen hours of wall-clock,
three runs the system never finished closing out, one task abandoned over failures the agent had no
part in, and two different headline percentages for the same run depending on which code path
printed it. One task that genuinely succeeded was recorded in the journal as having done no work at
all. All eight are fixed and the arm needs re-running.

- **Kind:** hand-run benchmark arm (`scripts/bench-run.sh`), **not** a dogfood run — no
  `dogfood-NNN` number, not in `dogfood-ledger.csv`
- **Date:** 2026-08-03 → 2026-08-04 (timestamps below are UTC)
- **Arm:** `benchmarks/results/p3-rung-4/chikory/20260803-131837-chikory` (gitignored; kept as the
  incident record)
- **Base HEAD:** `b6e27b5`
- **Arm config:** executor `gemini-cli`, judge `openai-compat` via the keyless codex proxy,
  budget $25/task, `max_steps` 60, `step_limits.max_seconds` 840, adapter cap 4 h
- **Reported:** `tasksVerified` 4/5 · I-SR 0.9333 · D-SR 0.8 · **$0.00** (CLI-OAuth meters nothing)
- **Actual:** ⛔ **not publishable.** 3 of 5 runs never sealed; 1 task had no green base; the

## Friction

### 🔴 F-246 — a CG-1 strike counted failures the agent had no part in

`agent-loop.ts:795` was the last counter in the codebase reading raw `record.status === "FAILED"`.
`isInfraStepFailure` already exempted `infraFailed` **and** the legacy `"step exceeded maxSeconds="`
prefix; the rotation counter already honoured it. CG-1 did not.

`brownfield-001` journaled exactly three steps:

| Step | Status | Reason |
|---|---|---|
| 0 | FAILED | `step exceeded maxSeconds=840; killed after 840.2s (1.00× cap)` |
| 1 | FAILED | `step exceeded maxSeconds=840; killed after 840.1s (1.00× cap)` |
| 2 | FAILED | `limit response deferred … via park-until-reset` |

3/3 → ESCALATE. **Zero of the three were the agent's.** Fixed by WP-578.

### 🔴 F-247 — an unattended arm waited for an approver who does not exist

`brownfield-001/adapter.log`, verbatim:

```
judge escalated: executor FAILED 3 consecutive steps (last: limit response deferred … via park-until-reset; no executor work was performed)
run is AWAITING_APPROVAL — answer with: chikory approve run-757420ce-99ff-426f-b517-5e1d784ec499 [--reject "<reason>"]
```

`unattended: { escalation: "seal_resumable_failed" }` already existed; the bench spec builder never
set it. The run waited out its remaining 4 h and was SIGKILLed, leaving the workflow `Running`
forever. Fixed by WP-579.

### 🔴 F-248 — a quota deferral erased work the executor had already done

A wall read off the executor's own stderr arrives **after** it ran, but the deferral overwrote the
real `StepRecord` with a synthetic one: empty diff, `ZERO_TOKENS`, cost 0, summary *"no executor work
was performed"*.

`brownfield-005`, from its journal:

| Journal idx | Time (UTC) | Entry |
|---|---|---|
| 3 | `03:15:55.123Z` | step 0 → FAILED park, "no executor work was performed" |
| 5 | `03:15:55.224Z` | checkpoint commits `5ac47158c` — **3 files, +100/−4** |

`5ac47158c` wires an `AbortController` through `httpBatchStreamLink.ts` and `dataLoader.ts` and adds
a streaming test. R4's probe (unsubscribe aborts the in-flight fetch) **cannot** pass on stock tRPC,
whose `httpBatchStreamLink` returns a no-op teardown. `brownfield-005` is a genuine 4/4 earned in
~3 minutes of executor work, recorded as having done nothing.

Second harm: `appendStepConsumption` wrote zero tokens into the ledger `decideLimitPacing` reads to
predict the next wall. Fixed by WP-580. **`plan.md`'s WP-577 row was corrected** — it had called this
task a false positive on an untouched workspace.

### 🔴 F-249 — a park slept past its own run's deadline

`decideLimitParkDelay` had no ceiling and no view of any deadline.

| Task | Reset read | Sleep | Cap | Result |
|---|---|---|---|---|
| `brownfield-005` | `Resets in 19h49m1s` (`retryAtMs: 1785884700596`) | 19h49m | 4 h | SIGKILL, never woke |
| `brownfield-002` | pacing-predicted | 6h36m | 4 h | overran (see F-250) |

A sleep that provably outlives its own run is a hang wearing durability's clothes. Fixed by WP-581:
seal FAILED-resumable instead; `chikory resume` recovers in seconds once quota returns.

### 🔴 F-250 — the harness deadline killed `bash`, not the process group

`benchmarks/harness/src/adapter.ts` had re-implemented bounded exec: `spawn("bash", …)` undetached,
`child.kill("SIGKILL")` on the direct child only. A grandchild holding stdout open keeps `close` from
firing. `brownfield-002` ran **9h47m against a 4h cap — 2.45×**, the exact overrun ratio of
F-59/WP-255, which `runBounded` fixed long ago with `detached: true` + `process.kill(-pid, …)`.
Forking a second bounded-exec is what let the old bug back in. Fixed by WP-582 — one implementation
again.

### 🔴 F-251 — Gemini's wall was filed against the Codex judge

Every `limit_observation` in all three journals:

```
endpointTarget: "openai-compat", family: "openai-compat"
reason: "Error: Individual quota reached. Please upgrade your subscription … Resets in 19h49m1s."
```

The message is Gemini's. The attribution came from `routing.stages.code`, which the bench spec pins
to `openai-compat` whenever the codex proxy is up — while `bench-run.sh` states the opposite intent
("the gemini-cli executor runs the code stage directly"). The cross-run ledger therefore learned the
**judge** endpoint was exhausted, and WP-568 member cooling would have sidelined the wrong agent.
Fixed by WP-583.

### 🔴 F-252 — two I-SRs for one run

| Path | Denominator | I-SR | D-SR |
|---|---|---|---|
| `summarize` → `summary.json` | base-verified only, 15 | **0.9333** (14/15) | 0.8 (12/15) |
| `buildArmDetail` → publication bundle | unfiltered, 19 | **0.8947** (17/19) | 0.7895 (15/19) |

The bundle path silently readmitted `brownfield-002`, whose base never went green — and
dogfood-123's AC-2 requires the published bundle to match `summary.json` byte-for-byte. Separately,
`perTask` recorded nothing about the three runs that never sealed. Fixed by WP-584.

### 🔴 F-253 — the rotation system was structurally inactive

No `agent_classes` in the bench spec ⇒ `agents.executorClass` undefined ⇒ `recordWallAndCheckPeer`
skipped ⇒ every wall parked. **5 walls, zero `agent_rotation` entries.** The whole WP-566…WP-576
system did nothing.

The obvious fix is a trap: the repo's own `agent-classes.yaml` lists `sonnet-5`/`opus-5` as adjacent
members, so wiring it into an arm would let a Gemini wall rotate the executor onto **Claude** —
against the standing directive, and publishing an I-SR measured on a mixed executor. That is F-165
arriving through a new door. Fixed by WP-585, which adds a bench-only class file, refuses any member
with `backend: anthropic`, and makes a named-but-unreadable registry an error instead of a silent
fallback to the Claude-bearing defaults.

### 🔴 F-254 — a pinned task did not pin its runtime

`brownfield-002`'s red base was blamed on "an unrelated vitest fd bug". Measured on a clean clone of
the pinned ref `a061eaa1`:

| Node | Result |
|---|---|
| 24.14.1 | `Test Files 153 passed (153)`, `Tests 1128 passed (1128)` |
| 24.15.0 | **SIGABRT** inside vitest 4.1.9 before a single test runs (reproduced twice), preceded by `File descriptor N opened in unmanaged mode twice` |

The repo's `engines` is `">=24"`, an open range, so the harness took the newest installed toolchain
and drew the broken one. A task that pins its repo to a 40-hex sha and then leaves the runtime to
"whatever is newest locally" is not reproducible. Fixed by WP-586 (`node_version` on the task
schema; `brownfield-002` pinned to `24.14.1`).
