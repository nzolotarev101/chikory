## `brownfield-001` — the result worth publishing

`brownfield-001` upgrades `zod` from 3.22.4 to the 4.x line across `ecyrbe/zodios`. The task file
predicts three non-mechanical breaks: two `src/api.ts` narrowing casts, a transitive `typescript`
bump (zod v4's `.d.cts` needs `NoInfer`, ≥5.4, against a repo pinned at 5.2.2) with `@types/node`
behind it, and two tests that hardcode zod v3's `ZodError` shape.

Graded workspaces, read directly:

| | `zod` | `typescript` | `@types/node` | peer range | score |
|---|---|---|---|---|---|
| Chikory | `4.4.3` | `5.5.4` | `20.14.9` | `^4.x` | **3/3**, dep 3 |
| raw Claude Code | `3.22.4` | `5.2.2` | `20.8.9` | `^3.x` | 2/3, **dep 0** |

Chikory did the migration, including both transitive bumps. Raw Claude Code left the pin untouched;
R1 failed, so R2 and R3 dependency-zeroed to 0.

The journal (`run-cf1327a5…`) shows the mechanism rather than luck:

| idx | Entry |
|---:|---|
| 3-4 | judge 0 → **`ROLLBACK`** at step 0 |
| 8-9 | judge 1 → `PROCEED` at step 1 |
| 11-12 | completion review: `no_architecture_violations` **fails** — "scan evidence is explicitly absent" |
| 15-16 | judge 3 → `PROCEED` at step 2 |
| 18-19 | completion review: `no_architecture_violations` passes on real evidence |
| 20 | `terminal` → `SUCCESS` |

A rejected first attempt, a re-judged second, and a completion review that refused its own first
answer for lack of evidence. That is the P3 thesis — durable execution plus an in-loop judge of a
different model family — doing the thing it exists to do, on the one task in the corpus a bare agent
loop did not finish.

This is also the task the harness marked `baseVerified: false`.

## Friction

### 🔴 F-255 — a bench class file could not declare the endpoints it exists to pin

`validateRegistry` rejected `benchmarks/agent-classes.bench.yaml` outright. Its `executor-bench` /
`judge-bench` classes redeclare the same real endpoints as the shipped `executor-default` /
`judge-default` **on purpose** — WP-585 made a bench arm name its own classes so a missed class-file
load fails loud instead of silently inheriting the Claude-bearing defaults. Global member-id
uniqueness read that intentional mirror as a collision.

Fixed: a repeated id is a conflict only when the two declarations describe *different* endpoints
(`membersEqual`). Cooldown state keyed by that id is correct either way, because it is the same
endpoint. `packages/sdk-ts/src/agents/registry.ts`.

### 🔴 F-256 — `agent_classes` and a derived `routing` block collided

`buildChikorySpec` set an explicit `routing` block whenever `OPENAI_COMPAT_BASE_URL` was set — which
`bench-run.sh` always sets. `parseTaskSpec` refuses `agent_classes` and `routing` together, because
routing is *derived* from the class members. Every task died before materializing a workspace.

The override predates WP-585 and only ever reproduced what `policyFromMembers` already computes.
Fixed: skip it when `agentClasses` is set. `benchmarks/harness/src/adapter.ts`.

### 🔴 F-257 — the arm demanded a Claude key it is forbidden to use

`spec.judge` defaulted to `{ family: "anthropic" }` (the opposite of the executor's family) and that
guess survived `agent_classes` being set. `missingProviderEnv` checks `spec.judge.family`
independently of `routing.stages`, so it demanded `ANTHROPIC_API_KEY` — which the bench arm never
sets, by standing directive. The derived routing had already pointed the judge stage at the class
member's own openai-compat transport.

Fixed: `judge` defaults to `{}` when `agentClasses` is set. Same file. The regression test runs with
no `ANTHROPIC_API_KEY` in env — the original test supplied one and masked this.

### 🔴 F-258 — `baseVerified` measured the agent's output, not the base

`chikoryAdapter` reported no `baseVerification` at all, so `runSuite` fell back to running the base
command against `ctx.workspaceDir`. By then `adapter.ts:433` has already copied Chikory's
**post-agent** workspace into that directory. The suite answered "was the base green?" by testing
the thing the agent produced.

It failed precisely where it mattered. `brownfield-001` is a dependency upgrade, so a
`--frozen-lockfile` install against the agent's correctly-rewritten `yarn.lock` could only fail:

```
error Your lockfile needs to be updated, but yarn was run with `--frozen-lockfile`.
```

Four independent confirmations the base is green:

1. The same pin, same `base_verification_command`, verified **green — 117 passed, 0 failed** through
   `commandAdapter` in the baseline arm, which verifies pre-agent.
2. `benchmarks/tasks/brownfield-001-dependency-major-upgrade.yaml:48` records the pin measured green
   on 2026-08-01 — 117 passed, 9 s.
3. A solo re-run of `brownfield-001` reproduced the identical failure — deterministic, not flaky.
4. The failure text is a lockfile complaint, not a test failure. Zero tests ran.

The other four tasks' `baseVerified: true` was luck: they do not perturb their lockfiles enough to
trip a frozen install. **No Chikory-arm run has ever measured what `baseVerified` claims to
measure.** A second hazard rode the same path — the fallback ran a full dependency install *inside
the graded workspace, immediately before `gradeTask`*.

Fixed by WP-587 in two places:

- `chikoryAdapter` verifies the pin itself, pre-agent, in a scratch clone at `outDir/base-verify`
  that it then deletes. Not in `ctx.workspaceDir`: the `cpSync(..., { force: true })` that follows
  *merges* rather than replaces, so a base-verify `node_modules` would survive into the graded
  artifact. Deleting the clone also keeps the disk footprint transient (dogfood-122 died of a full
  disk). Both adapters now go through one `verifyPinnedBase`, so `baseVerified` means the same thing
  in each arm down to the reason text.
- `runSuite`'s fallback no longer guesses. An adapter that reports nothing for a repo-pinned task
  gets a named un-verified verdict — *"adapter 'x' did not report a base verification for a
  repo-pinned task"* — because the workspace it would test has unknowable provenance from there.
  This closes the class, not the instance: the old fallback could manufacture a false **green** just
  as easily, and the suite regression test proves that direction.

### 🟠 F-259 — the promote step published whichever directory was newest

The canonical `<out>/summary.json` the two arms are compared from was promoted by hand with
`ls -d <out>/*-chikory | tail -1`. That is "newest directory", not "the arm". A one-task diagnostic
re-run of `brownfield-001` was sitting there (`20260806-010237-chikory`) when the promote step came
due, and it would have been published as the five-task arm.

Fixed by WP-587: `chikory-bench run` writes `<out>/summary.json` itself, and only when the run
covered the whole corpus. A `--filter brownfield-001` diagnostic can never clobber the canonical
file; `bench-run.sh`'s standing `--filter brownfield` (5 of 5) still promotes. Runbook step 4 is
gone.

### 🟠 F-260 — the baseline arm lived in an operator's notes and went stale

The raw Claude Code arm was a shell one-liner pasted from a runbook. It had drifted against the
installed CLI: `claude -p` / `--print` is a **boolean** flag, so `claude -p "$(cat {goalFile})" …`
passed the goal as a positional the CLI never consumed. The agent got an empty prompt, every task
no-op'd, and the arm produced a 3m41s null run that looked like a result
(`20260806-002019-command`). The working form puts the prompt on stdin.

Per CLAUDE.md — if it isn't runnable via devbox, it doesn't exist. Fixed by WP-587:
`scripts/bench-baseline.sh` + `devbox run bench-baseline`, carrying a loud note that **Claude here
is the system under measurement, not Chikory's executor**, so nobody "corrects" it to gemini later.
