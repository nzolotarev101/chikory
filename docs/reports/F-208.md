# Friction Report: F-208 — an answered node escalation left the chain un-sealed and un-resumable

- **Friction ID**: `F-208` (chain dead-ends after a rejected escalation)
- **Class**: `product`
- **Component**: `packages/sdk-ts` (`src/chain/chain-loop.ts`, `src/chain/advance.ts`, `src/cli/chain.ts`)
- **First Observed**: `dogfood-120` (`devbox run chain-dogfood`), `chain-0723ac0b-4eba-413a-933f-2d1646a4f643`, 2026-07-29
- **Fixed**: 2026-07-28 session, hand-landed as **WP-543**
- **Status**: **CLOSED** — live-proven in `test/chain/chain-escalation-seal-live.test.ts`

## Plain summary

A chain whose node escalation was rejected by a human, with its one automatic
retry spent, stopped without writing anything. No terminal seal, no in-flight
node, no command that could move it — `chain approve` and `chain resume` both
refused, while the plan, both node attempts, and the replan evidence sat intact
on disk. The chain now always seals, and the seal names the recovery command.

## What happened

| # | Step | Result |
|---|---|---|
| 1 | `N-1` judged out-of-rubric | child parked `AWAITING_APPROVAL` |
| 2 | human `chain approve --reject "…"` | `N-1` sealed `{status: FAILED, verdict: ESCALATE}` |
| 3 | replan budget (`maxReplans = 1`) | `N-1` → `N-1-r1` dispatched with the failure brief |
| 4 | `N-1-r1` escalated, rejected too | `N-1-r1` sealed `{status: FAILED, verdict: ESCALATE}` |
| 5 | `decideReplan` | `HALT` — budget spent, `resumableSeal = true` |
| 6 | `chainLoop` returned | **no `terminal` entry, `chains.status` still `RUNNING`** |
| 7 | `chikory chain resume` | `chain … has no in-flight node awaiting a decision` |

## Root cause

Not a CLI-routing bug — a **missing terminal transition** in the workflow.

- `deriveChainStatus` rule 1 (ADR-005 §S3): any node outcome with
  `verdict === "ESCALATE"` → `AWAITING_PLAN_APPROVAL`, "a human question
  outranks a mechanical failure".
- But that rule reads a **sealed** outcome, and a sealed escalation was
  **already answered** — the child blocks inside `executeChild` while it is
  `AWAITING_APPROVAL` and only seals once a human decides. The park it derives
  therefore has nobody left to unpark it.
- `chain-loop.ts` seals only on `SUCCESS` / `FAILED`, so it exited the loop in
  `AWAITING_PLAN_APPROVAL` and returned **without journaling anything**. The
  `resumableSeal = true` the HALT branch had already set was never used.

Everything downstream followed from the missing entry, not from its own logic:
`sealedChainState` reads `chains.status` (still `RUNNING`) → `resumeChain`
throws "no journal or is still live"; `inflightNode` finds every dispatched node
sealed → `chain approve` refuses; `followChain` waits on a terminal status that
is never written → `--watch` hangs. The unattended path (`unattended.escalation
= "seal_resumable_failed"`) reaches the same state with **no human involved at
all**, so this was never only an interactive-operator problem.

## Why it is a product gap

ADR-009 D1 is binding: *every* non-infra failure class gets at least one
bounded, journaled, automated heal attempt before any terminal seal. Here there
was no seal at all — strictly worse than a dead end, because the run could not
even be classified. The chain also printed `unblock with: chikory chain approve
…`, and following that exact instruction hit the refusal.

## The fix (WP-543)

1. **`src/chain/escalation-park.ts`** (new, pure) — `resolveAnsweredEscalationPark`
   converts the answered park into the resumable `FAILED` seal WP-521(c) already
   knows how to re-enter. ADR-005 §S3 puts non-node transitions in the
   orchestrator, so the four-rule reducer and its Python parity port
   (`chikory/chain_advance.py`) are byte-unchanged.
2. **`chain-loop.ts`** — resolves the park before the seal block; every
   incarnation now ends `SUCCESS` or `FAILED`, and `--watch` always returns.
3. **`decideChainOrphanRepair` + `repairOrphanedChainSeal`** — `chikory chain
   resume` repairs a chain already orphaned by the pre-fix workflow (write the
   missing seal, then re-enter). Fail-closed on an in-flight node, a live
   workflow, or an unreachable server.
4. **Actionable output** — the no-in-flight-node refusal now names
   `chikory chain resume <id> --watch`, and a resumable seal prints
   `recover with: …` at the seal instead of only in the docs.
