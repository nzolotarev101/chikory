# Friction Report: F-209 … F-214 — a chain node that never got its spec, and died on strikes it never earned

- **Friction IDs**: `F-209` (chain drops the node's execution policies) · `F-210`
  (rule-3 counts infra kills and reverted diffs) · `F-211` (remediation anchors on an
  empty checkpoint) · `F-212` (ROLLBACK masks the criterion feedback) · `F-213` (chain
  replan budget never forgives a healed node) · `F-214` (chain discards a resumable child)
- **Class**: `product`
- **Component**: `packages/sdk-ts` (`src/chain/`, `src/runner/`, `src/workflow/agent-loop.ts`)
- **First Observed**: `dogfood-120`, `chain-0723ac0b-4eba-413a-933f-2d1646a4f643`, node
  `N-2` (`chain-…-node-N-2`), 2026-07-29
- **Fixed**: 2026-07-29 session, hand-landed as **WP-544**
- **Status**: **CLOSED** — replay-proven against the real journal
  (`test/runner/strike-accounting.test.ts`) and live-proven
  (`test/chain/node-resume-live.test.ts`)

## Plain summary

The run that finally got past the plan gate (WP-542) and the seal gap (WP-543) died one
layer lower: node `N-2` was HALTed as a budget-waster after spending **$0.20 of $15**,
and the chain then refused it a single heal attempt because two *earlier* nodes — which
had since succeeded — had used up a chain-wide budget. Underneath both was a passthrough
gap nobody had ever looked at: the goal spec's `step_limits`, `unattended`, and `pacing`
blocks were parsed, validated, and then dropped before any node ran.

## The evidence

`N-2`'s journal, in full:

| step | executor | `scope_matches_instruction` | `N2-AC-1` | verdict |
|---|---|---|---|---|
| 0 | **FAILED** — `step exceeded maxSeconds=600; killed after 602.9s (1.00× cap)` | ✓ | ✗ strike 1 | PROCEED |
| 1 | SUCCESS | **✗** evidence report under `docs/reports/` | ✗ strike 2 | ROLLBACK — diff reverted |
| 2 | SUCCESS, scope already fixed | ✓ | ✗ strike 3 | **HALT** → remediation, restore to `@5` |
| 3 | SUCCESS — the one remediation attempt | ✓ | ✗ | HALT → seal FAILED `resumable: true` |

Two of the three fatal strikes were not the executor's work being judged. Chain journal,
last entry: `replan budget exhausted: 3 failed node(s) exceeds max 1` — the 3 being
`N-1`, `N-1-r1` (both spliced out of the plan) and `N-2`, against a budget of 1, on a
**six-node** plan whose `N-1` lineage had *succeeded* as `N-1-r1-r2`.

## Root cause

### F-209 — the node never got the spec

`cli/chain.ts` built `ChainNodeTemplate` from six fields; `node-spec.ts` projected those
onto the child `TaskSpec`. The persisted `N-2` spec:

```
keys: [acceptanceCriteria, budgetUsd, chainLink, executor, goal, judge, maxSteps, name, repos, routing]
stepLimits: None    unattended: None    pacing: None
```

The goal spec declared all three:

- `step_limits: {max_turns: 50, max_seconds: 840}` → dropped → the node ran the 600s
  `DEFAULT_STEP_LIMITS` → **step 0 was killed at 602.9s. That is strike 1.**
- `unattended: {escalation: seal_resumable_failed}` → dropped → **`N-1` parked
  `AWAITING_APPROVAL` for a human the spec had told it not to wait for — the trigger for
  F-208.**
- `pacing: {mode: auto, autoCalibrate: true}` → dropped → the WP-310 governor never ran.

One gap, two consecutive runs' headline failures.

### F-210 — the guard counted what it must not

Rule 3 calls itself a *goal drift / budget-waste* guard, which only holds if every
counted verdict judged work the executor produced and the workspace kept.

- **(a)** `infraFailed` (WP-263(b)) covered a killed judge *check*, never a killed
  executor *step*. A cap-killed step was judged anyway (`cadence: 1`) and its empty-diff
  fail entered the sequence.
- **(b)** `criteriaHistoryFromJournal` folded every verdict ever written; nothing
  truncated on a restore. The ROLLBACK strike described a tree that no longer existed —
  the executor was charged for the very state the judge told it to abandon.

### F-211 / F-212 — the heal attempt was set up to fail

`lastGoodCheckpointId` was set on any PROCEED, and the only PROCEED covered the
*timed-out* step. So the single remediation attempt rolled back to an empty tree and had
to redo steps 1 and 2 before it could start on the criterion. It also went in
half-informed: a rule-1 ROLLBACK rationale names only the destructive rubric item, and
`buildCriterionFeedback` was reachable **only** on the PROCEED branch — so at step 1 the
executor was told about the file placement and nothing about the substantive gap the
same judge form had recorded.

### F-213 / F-214 — the chain had one heal, and it was the destructive one

`decideReplan` compared a chain-wide count of *every* FAILED outcome the record had ever
held against a budget hardcoded to 1 in `runner.ts`. A lineage that failed twice and then
succeeded kept debiting forever. And `readNodeResult` never read `resumable` off the
terminal payload, so the chain's only answer to a failed node was `replanRemaining` —
rewriting the goal and dispatching a fresh empty workspace. `N-2` had sealed
`resumable: true` with a remediation brief, a checkpoint at `@21`, and **962 insertions**
of real work at `f7dee78`. The run said "re-enter me"; the chain could only say "start
over".

## The fix (WP-544)

| # | Change | Where |
|---|---|---|
| 1 | Template forwards `stepLimits`/`pacing`/`unattended`/`soak`/`notifications`/`horizon` | `chain/node-spec.ts`, `cli/chain.ts` |
| 2 | `CHAIN_TEMPLATE_FIELDS` classifies **every** `TaskSpec` key + a two-way compile-time assertion | `chain/node-spec.ts` |
| 3 | `StepRecord.infraFailed` (additive) set at both cap-kill sites; `judgeStep` stamps the pass | `types.ts`, `executors/step.ts`, `executors/native.ts`, `runner/activities.ts` |
| 4 | Rule-3 history truncates at the last ROLLBACK — **not** at a remediation restore | `runner/strike-accounting.ts`, `runner/activities.ts` |
| 5 | A PROCEED over a FAILED step is never the rollback anchor | `workflow/agent-loop.ts` |
| 6 | ROLLBACK/BRANCH/ESCALATE feedback carries the failing criteria too | `workflow/agent-loop.ts` |
| 7 | `decideReplan` takes `ReplanBounds`: per-lineage budget + chain ceiling over **live** plan nodes; `chain: {max_replans_per_node, max_replans}` in the goal spec | `chain/replan.ts`, `runner.ts`, `taskspec.ts` |
| 8 | `decideNodeHeal` → `resume_child` before `replan_node`; `node_resumed` journal kind | `chain/node-heal.ts`, `chain/chain-loop.ts`, `chain/activities.ts`, `chain/store.ts` |

**Deliberately not done:** the remediation restore does **not** clear the strike counter.
Remediation fires *because* the criterion is three verdicts stuck; resetting its own
trigger would turn one bounded heal into three more judge passes and weaken the bound
WP-519 exists to enforce. (Measured: doing so flipped three live tests from FAILED to
SUCCESS — the guard stopped guarding.)

## Recorded, not fixed here

- 🟡 **F-215** — the "budget-waste guard" HALTed at **$0.2025 of $15** (1.3%). All of it
  was judge spend: the CLI-OAuth executor meters $0, which is also why every
  `judge.maxCostShare` warning in the run read 100%. The rationale should quote real
  spend against budget, and `maxCostShare` needs a keyless-executor story.
- 🟡 **F-216** — `N-2` carried **one** acceptance criterion bundling provenance + pin +
  RED + GREEN + lockfile verification, making rule 3 all-or-nothing (`N-1-r1-r2` had 3).
  The plan gate should reject a node whose single AC hides N independent checkables.
- ℹ️ **F-217** — `scope_matches_instruction` FAILED at step 1 for
  `docs/reports/brownfield-004-evidence.md` and PASSED at step 3 with that same file (and
  `docs/reports/dogfood-121.md`) in the diff. The rubric is diff-base relative and not
  stable across a restore.
